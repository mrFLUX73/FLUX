# Supabase для FLUX

Миграция `supabase/migrations/0001_initial_schema.sql` создаёт основу MVP:

- профиль пользователя и автоматическое создание профиля после регистрации;
- текущие цели и настройки питания;
- общий каталог продуктов и личные продукты;
- приёмы пищи и позиции дневника со снимком КБЖУ на момент добавления;
- личные упражнения, планы тренировок и порядок упражнений по дням;
- тренировочные сессии и выполненные подходы.

## Локальный запуск

Нужны Docker и [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started).

Если в `supabase` ещё нет `config.toml`, один раз выполните:

```bash
supabase init
```

```bash
supabase start
supabase db reset
```

`db reset` применит все файлы из `supabase/migrations`. Миграция рассчитана на PostgreSQL 15+ (актуальный локальный стек Supabase). Значения локальных `API URL` и `anon key` выводятся командой `supabase status`. Скопируйте `.env.example` в `.env.local` и замените оба значения. Файлы `.env.local` и ключ `service_role` нельзя коммитить или передавать во фронтенд.

Для удалённого проекта:

```bash
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

## Модель доступа

Все API-таблицы защищены RLS и доступны только роли `authenticated`. Пользователь читает и изменяет только строки со своим `user_id`; принадлежность дочерних записей дополнительно закреплена составными внешними ключами.

Связи `план → упражнение` и `сессия → подход` задаются при создании записи и не меняются клиентом после этого. Если связь выбрана ошибочно, запись нужно удалить и создать заново; обычные поля вроде повторов, веса, порядка и заметок остаются редактируемыми.

У общего продукта `products.owner_id` равен `NULL`: его могут читать все вошедшие пользователи, но создавать, изменять и отмечать такие записи как проверенные должен только доверенный серверный код с `service_role`. Личный продукт всегда имеет `is_verified = false`. Клиент может создавать, менять и удалять только продукты, где `owner_id = auth.uid()`. Триггер также запрещает привязать позицию дневника к чужому личному продукту.

Названия продукта, упражнения и рассчитанные показатели сохраняются в дневнике и выполненных подходах как снимки. Поэтому история остаётся понятной после изменения или удаления исходной записи.

## Быстрая проверка перед интеграцией

1. Создайте двух тестовых пользователей A и B.
2. Убедитесь, что A не видит и не меняет профиль, дневник, планы и сессии B.
3. Убедитесь, что оба пользователя видят общий продукт, но не могут его изменить.
4. Убедитесь, что A не может добавить в дневник личный продукт B или перепривязать дочернюю запись к родительской записи B.
5. Проверьте каскадное удаление приёма пищи/сессии и сохранность снимков после удаления продукта.
